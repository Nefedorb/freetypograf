# DESIGN_SYSTEM.md

## 1. Назначение файла

Этот файл описывает правила дизайн-системы проекта.

Его нужно использовать вместе с официальным shadcn/ui skill:

https://ui.shadcn.com/docs/skills

shadcn/ui skill отвечает за корректное использование компонентов, CLI, `components.json`, темизации и паттернов shadcn/ui.

Этот файл отвечает за визуальную консистентность проекта: размеры, отступы, ширину элементов, типографику, аккуратность интерфейса, правила использования кнопок, форм, карточек и общую визуальную дисциплину.

Главный принцип:

**Не изобретать новый стиль для каждого экрана. Все страницы, формы, кнопки, карточки, таблицы и модальные окна должны выглядеть как части одной дизайн-системы.**

---

## 2. Общая цель дизайна

Интерфейс проекта должен быть аккуратным, современным, спокойным, читаемым, визуально консистентным, удобным на desktop и mobile, построенным на shadcn/ui и Tailwind CSS, без случайных размеров, цветов и отступов.

Дизайн не должен выглядеть как набор случайно сгенерированных блоков.

---

## 3. Базовые принципы

### 3.1. Консистентность важнее разнообразия

Используй существующие компоненты shadcn/ui.

Не создавай кастомные кнопки, инпуты, селекты, табы, модальные окна, dropdown, toast, table, card, badge и другие базовые элементы, если есть готовый компонент shadcn/ui.

Не смешивай разные стили карточек, кнопок и форм на одной странице.

Повторяй уже принятые размеры, отступы, радиусы, тени и типографику.

Если похожий элемент уже есть в проекте, новый элемент должен быть сделан в том же стиле.

### 3.2. Интерфейс не должен быть растянутым

По умолчанию не растягивай элементы на всю ширину экрана, если этого не требует сценарий.

Плохо:

<Button className="w-full">Сохранить</Button>
<Input className="w-full" />

Хорошо:

<Button>Сохранить</Button>
<Input className="max-w-sm" />

`w-full` допустим только когда:

- это мобильный экран;
- это форма в узкой колонке;
- это таблица, список, карточка или layout-блок;
- кнопка должна занять всю ширину по смыслу, например в карточке тарифа;
- инпут находится внутри формы с фиксированной максимальной шириной;
- элемент является частью grid/flex-layout и должен занимать доступное пространство.

На desktop кнопки и инпуты обычно не должны быть огромными.

### 3.3. Сначала смысл, потом украшения

Интерфейс должен помогать пользователю выполнить действие.

Не добавляй декоративные элементы, если они не улучшают понимание.

Не перегружай экран иконками, цветами, бейджами, тенями и анимациями.

Один экран должен иметь понятную визуальную иерархию:

1. главный заголовок;
2. краткое пояснение;
3. основной контент;
4. главное действие;
5. второстепенные действия.

## 4. Layout и ширина контента

### 4.1. Контейнеры

Используй ограниченную ширину основного контента.

Рекомендуемый базовый контейнер:

<div className="container mx-auto px-4 md:px-6 lg:px-8">

Рекомендуемые максимальные ширины:

- Узкий текстовый контент: `max-w-2xl`
- Формы и настройки: `max-w-xl`
- Средние страницы: `max-w-4xl`
- Широкие страницы: `max-w-5xl`
- Дашборды и таблицы: `max-w-6xl` или `max-w-7xl`
- Hero-блоки: `max-w-5xl` или `max-w-6xl`

Не делай текстовые блоки на всю ширину экрана.

Плохо:

<p className="w-full text-lg">

Хорошо:

<p className="max-w-2xl text-muted-foreground">

### 4.2. Вертикальные отступы

Используй предсказуемую шкалу отступов.

Между секциями:

`py-12`, `py-16`, `py-20`

Внутри карточек:

`p-4`, `p-6`, `p-8`

Между элементами формы:

`space-y-4`, `space-y-6`

Между заголовком и описанием:

`space-y-2`

Между группами блоков:

`gap-4`, `gap-6`, `gap-8`

Не используй случайные значения вроде:

`mt-[37px]`, `p-[19px]`, `gap-[23px]`

Arbitrary values допустимы только если есть строгая причина.

### 4.3. Горизонтальные отступы

Для страниц:

`px-4 md:px-6 lg:px-8`

Для карточек:

`p-4 md:p-6`

Для крупных маркетинговых секций:

`p-6 md:p-8 lg:p-10`

Не делай слишком плотные блоки без воздуха.

## 5. Сетка

### 5.1. Базовые grid-паттерны

Для карточек:

<div className="grid gap-4 md:grid-cols-2 lg:grid-cols-3">

Для статистики:

<div className="grid gap-4 md:grid-cols-2 lg:grid-cols-4">

Для двухколоночного layout:

<div className="grid gap-8 lg:grid-cols-2">

Для sidebar layout:

<div className="grid gap-8 lg:grid-cols-[240px_1fr]">

### 5.2. Не ломать сетку

Не используй случайные ширины колонок без необходимости.

Плохо:

<div className="grid grid-cols-[37%_63%]">

Хорошо:

<div className="grid gap-8 lg:grid-cols-[320px_1fr]">

## 6. Типографика

### 6.1. Размеры шрифтов

Используй ограниченную шкалу размеров.

H1:

`text-3xl md:text-4xl lg:text-5xl font-semibold tracking-tight`

H2:

`text-2xl md:text-3xl font-semibold tracking-tight`

H3:

`text-xl md:text-2xl font-semibold`

H4:

`text-lg font-medium`

Основной текст:

`text-sm md:text-base`

Малый текст:

`text-sm text-muted-foreground`

Caption:

`text-xs text-muted-foreground`

### 6.2. Правила для текста

Не используй слишком много `font-bold`.

Для большинства заголовков используй `font-semibold`.

Для вторичного текста используй `text-muted-foreground`.

Для длинного текста используй ограничение ширины: `max-w-prose`, `max-w-xl`, `max-w-2xl`.

Не используй больше 2–3 размеров шрифта в одном блоке.

Не делай весь интерфейс крупным. Большой текст нужен только для hero, заголовков и ключевых чисел.

### 6.3. Длина строк

Текст не должен быть слишком длинным.

Хорошо:

<p className="max-w-2xl text-muted-foreground">

Плохо:

<p className="w-full text-muted-foreground">

### 6.4. Tracking

Для крупных заголовков используй `tracking-tight`.

Не используй `tracking-widest` для обычного интерфейса.

## 7. Кнопки

### 7.1. Использование

Всегда используй компонент `Button` из shadcn/ui.

import { Button } from "@/components/ui/button"

Не создавай кастомную кнопку через `<div>` или `<a>` без необходимости.

Плохо:

<div onClick={save} className="cursor-pointer rounded bg-black px-4 py-2 text-white">
  Сохранить
</div>

Хорошо:

<Button onClick={save}>Сохранить</Button>

### 7.2. Размеры кнопок

По умолчанию используй стандартный размер:

<Button>Сохранить</Button>

Для компактных действий:

<Button size="sm">Изменить</Button>

Для hero-блоков или главных CTA:

<Button size="lg">Начать бесплатно</Button>

Не делай все кнопки большими.

### 7.3. Ширина кнопок

Кнопки не должны быть слишком длинными.

Плохо:

<Button className="w-full max-w-3xl">Сохранить</Button>

Хорошо:

<Button>Сохранить</Button>
<Button className="w-fit">Создать ссылку</Button>
<Button className="w-full sm:w-auto">Продолжить</Button>

Для группы кнопок:

<div className="flex flex-col gap-3 sm:flex-row">
  <Button>Основное действие</Button>
  <Button variant="outline">Вторичное действие</Button>
</div>

На мобильных кнопки могут быть на всю ширину, но на desktop должны возвращаться к естественной ширине:

<Button className="w-full sm:w-auto">
  Продолжить
</Button>

### 7.4. Иерархия кнопок

На одном экране не должно быть много главных кнопок.

Используй варианты:

- `default` — главное действие;
- `secondary` — второстепенное действие;
- `outline` — альтернативное действие;
- `ghost` — тихое действие;
- `destructive` — опасное действие.

Не используй `destructive` для обычных красных акцентов.

Опасные действия:

<Button variant="destructive">Удалить</Button>

Вторичные действия:

<Button variant="outline">Отмена</Button>

### 7.5. Тексты кнопок

Текст кнопки должен быть коротким.

Хорошо:

- `Сохранить`
- `Создать`
- `Продолжить`
- `Добавить ссылку`
- `Открыть отчет`

Плохо:

- `Нажмите сюда, чтобы сохранить все изменения в настройках`
- `Кликните для перехода на следующий этап`

## 8. Инпуты и формы

### 8.1. Общие правила

Используй компоненты shadcn/ui:

- `Input`
- `Textarea`
- `Select`
- `Checkbox`
- `RadioGroup`
- `Switch`
- `Field`
- `FieldGroup`
- `Label`

Для форм следуй паттернам shadcn/ui.

Если в проекте используется `FieldGroup`, используй его для группировки полей.

### 8.2. Ширина форм

Формы не должны растягиваться на весь экран.

Для короткой формы:

<form className="w-full max-w-md space-y-4">

Для настроек:

<form className="w-full max-w-xl space-y-6">

Для сложной формы:

<form className="w-full max-w-2xl space-y-8">

Плохо:

<form className="w-full max-w-7xl">

### 8.3. Ширина инпутов

Инпуты не должны быть огромными на desktop.

Плохо:

<Input className="w-full" />

Допустимо только внутри контейнера с ограниченной шириной:

<div className="max-w-md">
  <Input />
</div>

Хорошо:

<Input className="max-w-sm" />

Или:

<div className="w-full max-w-md space-y-2">
  <Label htmlFor="email">Email</Label>
  <Input id="email" type="email" />
</div>

### 8.4. Подписи и ошибки

У каждого поля должна быть понятная подпись.

<div className="space-y-2">
  <Label htmlFor="email">Email</Label>
  <Input id="email" type="email" placeholder="name@example.com" />
  <p className="text-sm text-muted-foreground">
    Используем только для уведомлений.
  </p>
</div>

Ошибки показывай рядом с полем:

<p className="text-sm text-destructive">
  Введите корректный email
</p>

### 8.5. Placeholder

Placeholder не заменяет label.

Плохо:

<Input placeholder="Email" />

Хорошо:

<div className="space-y-2">
  <Label htmlFor="email">Email</Label>
  <Input id="email" placeholder="name@example.com" />
</div>

### 8.6. Группы полей

Похожие поля группируй визуально.

<div className="grid gap-4 md:grid-cols-2">
  <div className="space-y-2">
    <Label htmlFor="firstName">Имя</Label>
    <Input id="firstName" />
  </div>

  <div className="space-y-2">
    <Label htmlFor="lastName">Фамилия</Label>
    <Input id="lastName" />
  </div>
</div>

## 9. Карточки

### 9.1. Использование

Для группировки информации используй `Card`.

<Card>
  <CardHeader>
    <CardTitle>Название</CardTitle>
    <CardDescription>Описание блока</CardDescription>
  </CardHeader>
  <CardContent>
    ...
  </CardContent>
</Card>

### 9.2. Плотность

Стандартные внутренние отступы:

<CardContent className="p-6">

Для компактных карточек:

<CardContent className="p-4">

Для крупных маркетинговых блоков:

<CardContent className="p-8">

### 9.3. Не перегружать карточки

В одной карточке должен быть один смысловой блок.

Плохо:

- карточка с формой, статистикой, таблицей, графиком и настройками одновременно.

Хорошо:

- отдельная карточка для формы;
- отдельная карточка для статистики;
- отдельная карточка для таблицы;
- отдельная карточка для графика.

### 9.4. Карточки одинакового типа должны быть одинаковыми

Если на экране есть сетка карточек, они должны иметь одинаковые:

- отступы;
- радиусы;
- высоту или структуру;
- стиль заголовков;
- стиль описаний;
- расположение действий.

## 10. Цвета

### 10.1. Использовать semantic tokens

Не используй случайные цвета напрямую, если можно использовать токены темы.

Хорошо:

`text-foreground`, `text-muted-foreground`, `bg-background`, `bg-muted`, `bg-card`, `border-border`, `text-primary`, `bg-primary`, `text-destructive`

Плохо:

`text-gray-500`, `bg-white`, `border-gray-200`, `text-red-600`

Исключения:

- брендовые иллюстрации;
- графики;
- специальные промо-блоки;
- явно заданные фирменные цвета;
- внешние embed-блоки.

### 10.2. Не злоупотреблять акцентами

Один главный акцент на экране.

Не делай все кнопки, иконки и заголовки акцентными.

Вторичный текст — через `text-muted-foreground`.

Границы — через `border-border`.

Фон второстепенных блоков — через `bg-muted`.

### 10.3. Статусы

Для статусов используй `Badge`.

Примеры:

<Badge>Активно</Badge>
<Badge variant="secondary">Черновик</Badge>
<Badge variant="destructive">Ошибка</Badge>
<Badge variant="outline">Архив</Badge>

Не используй случайные цветные плашки, если можно использовать `Badge`.

## 11. Радиусы, тени и границы

### 11.1. Радиусы

Используй радиусы из темы shadcn/ui.

Рекомендуемые классы:

`rounded-md`, `rounded-lg`, `rounded-xl`, `rounded-2xl`

Не используй случайные значения:

`rounded-[13px]`

### 11.2. Тени

Используй тени умеренно.

Допустимые варианты:

`shadow-sm`, `shadow`

Не делай тяжелые тени без необходимости:

`shadow-2xl`

Для большинства SaaS-интерфейсов достаточно:

`border bg-card`

### 11.3. Границы

Используй:

`border`, `border-border`

Не используй разные цвета границ на одной странице без смысла.

---

## 12. Иконки

Используй одну библиотеку иконок во всем проекте.

Если проект использует `lucide-react`, не подключай другие наборы без необходимости.

Размеры иконок:

- `size-4` — внутри кнопок, меню, таблиц;
- `size-5` — обычные интерфейсные иконки;
- `size-6` — крупные иконки в карточках;
- `size-8` — empty state или hero.

Иконки должны помогать пониманию, а не украшать каждый элемент.

Плохо:

- иконка у каждого пункта без смысла;
- разные стили иконок в одном блоке;
- слишком крупные иконки в таблице.

Хорошо:

<Button>
  <Plus className="mr-2 size-4" />
  Создать
</Button>

---

## 13. Таблицы и списки

### 13.1. Таблицы

Используй таблицы для структурированных данных.

Правила:

- не делай таблицу шире контента без необходимости;
- используй компактную высоту строк;
- действия в строках размещай справа;
- для пустых значений используй `—`;
- для статусов используй `Badge`;
- не перегружай таблицу кнопками;
- основные действия выноси в меню или правую колонку.

### 13.2. Строки таблиц

Действия в строке должны быть компактными.

Хорошо:

<Button variant="ghost" size="icon" aria-label="Открыть меню">
  <MoreHorizontal className="size-4" />
</Button>

Плохо:

<Button className="w-full">Редактировать эту запись</Button>

### 13.3. Списки

Для списков настроек или сущностей используй карточки или строки с одинаковой структурой:

<div className="divide-y rounded-lg border">
  <div className="flex items-center justify-between p-4">
    ...
  </div>
</div>

## 14. Empty states

Для пустых состояний всегда показывай:

1. короткий заголовок;
2. пояснение;
3. следующее действие, если оно есть.

Пример:

<div className="flex min-h-[320px] flex-col items-center justify-center rounded-lg border border-dashed p-8 text-center">
  <h3 className="text-lg font-medium">Пока нет ссылок</h3>
  <p className="mt-2 max-w-sm text-sm text-muted-foreground">
    Создайте первую отслеживаемую ссылку, чтобы увидеть статистику.
  </p>
  <Button className="mt-4">Создать ссылку</Button>
</div>

Empty state не должен выглядеть как ошибка.

---

## 15. Модальные окна, Sheet и Drawer

### 15.1. Что использовать

Используй:

- `Dialog` для коротких действий;
- `AlertDialog` для опасных подтверждений;
- `Sheet` для боковых панелей;
- `Drawer` для мобильных сценариев, если это уместно.

### 15.2. Правила

У модального окна должен быть понятный заголовок.

Не помещай большие сложные формы в маленький `Dialog`.

Кнопка отмены должна быть визуально слабее основной.

Опасное действие всегда требует подтверждения.

Пример:

<AlertDialog>
  ...
  <AlertDialogAction>Удалить</AlertDialogAction>
  <AlertDialogCancel>Отмена</AlertDialogCancel>
</AlertDialog>

## 16. Адаптивность

### 16.1. Mobile-first

Сначала делай нормальный мобильный интерфейс, затем расширяй для desktop.

Частые паттерны:

`className="grid gap-4 md:grid-cols-2 lg:grid-cols-3"`

`className="flex flex-col gap-3 sm:flex-row"`

`className="px-4 md:px-6 lg:px-8"`

`className="text-3xl md:text-4xl"`

### 16.2. Кнопки на мобильных

На мобильных кнопки могут быть `w-full`, но на desktop должны возвращаться к естественной ширине:

<Button className="w-full sm:w-auto">
  Продолжить
</Button>

### 16.3. Формы на мобильных

Инпуты на мобильных обычно занимают всю ширину контейнера.

Но сам контейнер формы должен иметь ограничение на desktop:

<div className="w-full max-w-md">
  <Input />
</div>

### 16.4. Таблицы на мобильных

Если таблица плохо помещается на мобильных:

- используй горизонтальный scroll;
- либо преврати строки таблицы в карточки;
- не сжимай колонки до нечитаемого состояния.

## 17. Состояния интерфейса

Для каждого интерактивного сценария учитывай состояния:

- default;
- hover;
- active;
- disabled;
- loading;
- error;
- empty;
- success.

### 17.1. Loading

Для загрузки используй:

- `Skeleton` для контента;
- disabled-кнопку со spinner для отправки формы.

Пример:

<Button disabled>
  <Loader2 className="mr-2 size-4 animate-spin" />
  Сохраняем
</Button>

### 17.2. Disabled

Disabled-элементы должны выглядеть неактивными.

Если действие недоступно, объясни почему через текст, tooltip или helper text.

### 17.3. Error

Ошибки должны быть понятными.

Плохо:

Error 400

Хорошо:

Не удалось сохранить изменения. Проверьте поля и попробуйте снова.

### 17.4. Success

Успешное действие должно давать обратную связь:

- toast;
- inline-сообщение;
- изменение статуса;
- переход к следующему шагу.

---

## 18. Доступность

Обязательные правила:

- у каждого `Input` должен быть связанный `Label`;
- не используй div-кнопки;
- интерактивные элементы должны быть доступны с клавиатуры;
- не убирай `focus-visible` стили;
- иконка без текста должна иметь `aria-label`;
- цвет не должен быть единственным способом передачи смысла;
- текст ошибки должен быть рядом с полем;
- модальные окна должны иметь заголовок;
- у изображений должен быть осмысленный `alt`, если изображение несет смысл.

Плохо:

<X onClick={close} />

Хорошо:

<Button variant="ghost" size="icon" aria-label="Закрыть" onClick={close}>
  <X className="size-4" />
</Button>

---

## 19. Анимации

Анимации должны быть короткими и спокойными.

Допустимо:

`transition-colors`, `transition-all`, `duration-200`

Не делай:

- долгие анимации;
- постоянное движение;
- прыгающие элементы;
- анимации, мешающие чтению;
- разные стили анимации на одной странице.

Анимация должна помогать интерфейсу, а не отвлекать.

## 21. Что нельзя делать

Не делай:

- кнопки на всю ширину desktop-экрана без причины;
- инпуты на всю ширину большого контейнера без ограничения;
- формы шириной `max-w-7xl`;
- текстовые блоки шириной во весь экран;
- случайные размеры через arbitrary values;
- много разных радиусов на одной странице;
- много разных теней;
- несколько главных CTA рядом;
- кастомные компоненты вместо shadcn/ui без необходимости;
- хардкод цветов вместо semantic tokens;
- слишком крупные кнопки в обычных интерфейсах;
- слишком длинные плейсхолдеры;
- интерфейс без empty/loading/error states;
- модальные окна с огромным количеством полей;
- таблицы без адаптации под мобильные экраны;
- декоративные иконки в каждом пункте без смысла;
- слишком много `font-bold`;
- случайные `z-index`;
- хаотичные `margin` и `padding`;
- смешение разных UI-библиотек без причины.

## 22. Правила для генерации нового UI

Когда создаешь новый экран или компонент:

1. Сначала проверь, есть ли подходящий компонент shadcn/ui.
2. Используй существующие токены темы.
3. Ограничь ширину контента.
4. Не растягивай кнопки и инпуты без причины.
5. Используй повторяемые размеры отступов.
6. Используй понятную типографическую иерархию.
7. Добавь состояния loading, empty и error, если они нужны.
8. Проверь мобильную адаптацию.
9. Проверь доступность.
10. Убери лишние декоративные элементы.
11. Сравни новый UI с уже существующими экранами проекта.

---

## 23. Правила для рефакторинга UI

При изменении существующего интерфейса:

- не меняй визуальный стиль без причины;
- не ломай существующую сетку;
- не заменяй shadcn/ui компоненты на кастомные;
- не добавляй новые цвета, если можно использовать текущие;
- сохраняй текущую визуальную иерархию;
- исправляй неконсистентные размеры кнопок, инпутов, карточек;
- убирай лишние `w-full`, если они растягивают элементы;
- убирай случайные arbitrary values;
- делай интерфейс проще, а не сложнее;
- сохраняй доступность;
- не удаляй важные состояния интерфейса.

## 25. Мини-чеклист для Codex / агента

- не выглядит ли интерфейс случайно собранным.

## 26. Короткая инструкция для агента

При любой задаче по UI:

1. Прочитай этот файл.
2. Используй shadcn/ui по умолчанию.
3. Не создавай кастомные UI primitives, если есть готовый shadcn/ui компонент.
4. Не растягивай кнопки и инпуты на всю ширину desktop-экрана без причины.
5. Используй semantic theme tokens вместо hardcoded colors.
6. Сохраняй единые размеры шрифтов, отступов, радиусов и карточек.
7. Проверяй mobile-версию.
8. Делай интерфейс спокойным, чистым и предсказуемым.
9. В конце проверь раздел “Мини-чеклист для Codex / агента”.
